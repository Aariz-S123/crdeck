# crdeck: Clash Royale ML deck builder

A personal deck-building assistant. Give it 0–3 cards and it returns legal 8-card decks with an archetype, an estimated win rate (with sample size and uncertainty), synergy evidence, advisory warnings and swap suggestions, all learned from top-player battles collected through the official API. Spec: [docs/spec.md](docs/spec.md).

Learning project; not affiliated with Supercell. It does not find "the best deck." Win rates describe top-player battles in the sampled window, not your games, and synergy scores are correlations, not proven combos.

## Real data, step by step

1. Create a key at developer.clashroyale.com for your **current public IP** (keys are IP-bound). Copy `.env.example` to `.env` and set `CR_API_KEY`.
2. `python -m crdeck gate`: fetches `/cards`, the Path of Legends leaderboard and one battle log, then prints a field inventory. Paste it into [docs/api-notes.md](docs/api-notes.md) and fix anything in `config/collection.yaml` that turns out different (battle type string, evolution field, hero field, leaderboard endpoint).
3. Review `data/labels/cards.csv` (start with rows that have a note; see `data/labels/cards_label_report.md`), then bump `label_version`.
4. `python -m crdeck collect`: battle logs for the top players. Cached and resumable; nothing already in `data/raw/<window>` is fetched again. A log holds only recent battles, so collect across days with a new `window.id` each time to reach tens of thousands of battles.
5. `python -m crdeck build`: rebuilds `data/interim` and `data/processed` from raw data plus labels.
6. Archetypes: `python -m crdeck label` writes a k-means worklist to `data/processed/archetype_worklist.csv`. Label 20 decks as `heldout` **first**, then 60–80 as `train`, in `data/labels/archetype_labels.csv` (`deck_key,archetype,split,labeled_at,notes`).
7. `python -m crdeck evaluate`, then open the notebooks.

`python -m crdeck suggest "Hog Rider" "Knight@evo"` prints decks with full explanations. Forms: `@evo`, `@hero`.

## Synthetic data (pipeline testing only)

```bash
python -m crdeck synthetic
python -m crdeck build --source synthetic
python -m crdeck suggest --source synthetic "Hog Rider"
CRDECK_DATA_SOURCE=synthetic python scripts/run_notebooks.py
```

Generated battles go to `data/synthetic/` (git-ignored), and every output is labeled SYNTHETIC. They use real card names so decks are readable, but card strengths and pair bonuses are random and planted (`data/synthetic/truth.json`), which is how the tests check the models recover a known signal. This is never a fallback: the default source is `real`, and with no real data every step stops with an error saying what to run.

## Layout

```
config/          deck_rules.yaml (slot rules), collection.yaml (API, window, forms, split), model.yaml
data/labels/     cards.csv (hand labels), source/cards_meta.csv (your original CSV), archetype labels
data/raw/        immutable API responses, one file per request (git-ignored)
src/crdeck/      cards, rules (only legality code), api (only network code), collect, parse, dataset,
                 synergy, strength, archetype, search, explain, evaluate, pipeline, synthetic, cli
tests/           pytest: rules, parsing/dedupe, shrinkage, search invariants, API client, pipeline
notebooks/       01_cards … 07_demo (generated by scripts/make_notebooks.py; committed without outputs)
docs/            spec.md, api-notes.md (documented vs observed), model-notes.md (choices and deviations)
```

## Where this departs from the spec

See [docs/model-notes.md](docs/model-notes.md). In short:

- Synergy's expected rate uses each card's games without its partner, which fixes double counting.
- Completion adds a co-occurrence term tuned on the validation window.
- L2 strength is tuned on validation.
- The score interval includes model uncertainty.
- An `UNSEEN_DECK` flag marks extrapolated scores.
